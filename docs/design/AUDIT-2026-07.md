### 1. Agent can't run in the guest at all: no session/desktop story, no deployment, no autostart

**Severity:** high · **Area:** agent-capture

Nothing anywhere in the repo addresses how oxagent.exe actually runs inside a Windows guest. There is no installer, no service wrapper, no Run-key/Startup/Task-Scheduler entry, no firewall rule, no log destination. This is not a "later" problem — every option has a hard constraint that changes the agent's architecture: (a) run as a Windows service → Session 0 isolation, the agent sees no user windows and WGC returns nothing; (b) run in the interactive session → something must launch it after logon, and if that session is an RDP session (which is exactly how the winpodx dockur/windows guest at 127.0.0.1:3390 is reached), disconnecting the RDP client tears down/disconnects the session and DWM stops compositing, so WGC frame delivery stops — the agent silently goes dark; (c) UAC / secure desktop / lock screen run on a different desktop that WGC cannot capture at all, so any elevation prompt freezes the stream with no in-band signal to the client. The production shape used by RustDesk et al. is service-in-session-0 + WTSGetActiveConsoleSessionId/WTSQueryUserToken + CreateProcessAsUser to spawn a per-session worker, plus desktop-switch detection via OpenInputDesktop/SetThreadDesktop — none of which exists, and none of which is in the roadmap. Also practical blockers on day one of P1d: binding a TcpListener in the guest triggers a Windows Firewall prompt nobody will see (inbound silently blocked → the Linux client just hangs), the listener must bind 0.0.0.0 not 127.0.0.1, and the winpodx container needs a port mapping for the oxproto port the way 3390 is mapped for RDP. crates/oxagent/src/win.rs:65 also logs with eprintln!, which goes nowhere for a process autostarted without a console.

**Fix.** Before P1c, write docs/design/agent-runtime.md fixing the session model, and validate it: decide session-0 service + CreateProcessAsUser worker (needs windows features Win32_System_RemoteDesktop + Win32_Security + Win32_System_Threading) vs. logon-task worker. Add a `netsh advfirewall firewall add rule name=oxagent dir=in action=allow program=...` step and a guest port mapping. Replace eprintln! with a file logger under %LOCALAPPDATA%\oxagent. Test the RDP-disconnect case explicitly — capture surviving disconnect is a go/no-go for the whole winpodx use case.

### 2. Three disagreeing coordinate spaces and no DPI awareness — seamless windows will be misaligned

**Severity:** high · **Area:** agent-capture

For a seamless per-app window you must reconcile three different rectangles and the code uses the wrong one and knows about only one. (1) `GetWindowRect` (win.rs:51) on Win10/11 includes DWM's invisible resize border — typically ~7-8 px on left/right/bottom — so a Linux window sized from it is oversized and offset relative to what the user sees; the correct visible bounds come from DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS). (2) The WGC `GraphicsCaptureItem.Size` / frame texture dimensions are a third value again, and are physical pixels. (3) The process never calls SetProcessDpiAwarenessContext, so it is DPI-unaware: on a >100% DPI guest, GetWindowRect returns virtualized logical coordinates while WGC hands back physical-pixel textures, so reported geometry and texture size disagree by the scale factor, and any future SendInput coordinate mapping is scaled wrong. A 100%-DPI test guest hides all of this until the first HiDPI user. The protocol compounds it: WindowCreated carries exactly one (x,y,w,h) with no documented space and no scale factor (crates/oxproto/src/message.rs:39-47), so the client has no way to distinguish frame size from window size.

**Fix.** Call SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2) as the first statement in main (needs Win32_UI_HiDpi). Use DWMWA_EXTENDED_FRAME_BOUNDS for the geometry published to the client, keep GetWindowRect only for the capture↔window offset, and add explicit frame_width/frame_height + dpi_scale fields to WindowCreated/FrameData so the client can letterbox/scale correctly.

### 5. No cursor protocol — the default fallback (cursor baked into the frame) is the single worst perceived-latency defect available

A single 1080p RAW_BGRA frame is 8.3 MB and a 4K one is 33.2 MB; while that one message is on the wire, every pointer event, every keystroke, and every other window's frame is stuck behind it. That is self-inflicted head-of-line blocking inside the application layer — and it is exactly what RDP avoids by chunking virtual-channel data into ~1600-byte CHANNEL_PDU chunks and by having a fast-path input path. QUIC does not rescue this: on a single QUIC stream you get the identical stall, and the envelope has no stream/channel field to spread messages across streams. This is also the reason the clipboard and audio gaps below are structural, not additive — a multi-MB clipboard image or a continuous audio stream cannot share this wire with video without stalling it. Critically, fixing this changes the envelope, and there is currently no version/extension mechanism that lets the envelope change gracefully.

**Fix.** Redesign the envelope now, before oxagent/oxclient are built on it: `type u8 | flags u8 (FRAG_START/FRAG_END/priority) | channel_id u16 | len u32`. Cap a wire chunk at a latency-bounded size (e.g. 16-64 KiB) and fragment larger payloads. Define priority classes (input > cursor > audio > video > clipboard/bulk) and let the writer interleave. Map channels onto per-window QUIC streams and input onto QUIC datagrams later.

### 20. WGC frame-loop correctness pitfalls the P1c spec does not mention

**Severity:** medium · **Area:** agent-capture

### 23. No frame pacing, no backpressure, and no defined clock — latency will grow unbounded on any non-loopback link

### 39. Pre-auth memory amplification: a 5-byte header forces a 64 MiB zero-filled allocation before any payload byte arrives

**Severity:** medium · **Area:** protocol-design

Use `spare_capacity_mut` + `set_len` or `read_buf` to avoid the per-frame zero-fill on the hot path.

### 46. Alpha and color handling are unplanned — rounded corners, shadows and gamma will be visibly wrong

**Severity:** low · **Area:** client-and-display

WGC frames are BGRA with a live alpha channel, and modern Windows windows have rounded corners, drop shadows, and per-pixel transparency from DWM. Presenting those as seamless native Linux windows requires an alpha-capable path end to end, and none of it is decided: on X11 the window must be created on a 32-bit ARGB visual with its own colormap (the default visual is 24-bit and will render the corners black or opaque), on Wayland the surface must not be marked opaque and the buffer format must carry alpha, and on the wgpu side the surface must be configured with a CompositeAlphaMode of PreMultiplied or PostMultiplied with a matching premultiplication convention — WGC's output premultiplication has to be checked and matched or the edges will fringe. Configure wgpu surfaces as Bgra8Unorm (not the Srgb variant) with an explicitly chosen CompositeAlphaMode, and require the X11 backend to select a 32-bit ARGB visual plus colormap at window creation. Add a transparency test case (a window with rounded corners over a colored background) to the P2b acceptance criteria.

### 52. Envelope `payload_len` is decorative — the decoder ignores it, so frames silently read across message boundaries

**Severity:** low · **Area:** protocol-design

`Message::decode` (message.rs:297-303) reads the length into `_payload_len` and never uses it to bound the payload. Payload decoders read straight from the outer cursor, so an inner length field can overrun the frame. I verified both failure modes against the real code: (a) a FRAME_DATA frame declaring `payload_len = 0` with 17 real payload bytes decodes successfully to `FrameData { window_id: 7, timestamp: 99, data: [170,187,204] }`; (b) a WINDOW_CREATED frame declaring `payload_len = 22` but `title_len = 8` silently consumed 8 bytes spanning the *next* frame's header and payload, yielding `title: "\u{12}\u{4}\0\0\0AAA"` with no error. Reject (or explicitly document as forward-compat padding) any unconsumed remainder in that sub-cursor. Add `Message::decode_frame(&[u8]) -> DecodeResult<(Message, usize)>` returning bytes consumed, and a framed-iterator helper. Add regression tests for lying-length, truncated-payload, and concatenated-frame cases.

### 56. Envelope length is written with an unchecked `as u32` cast, so encode and header can silently disagree

**Severity:** low · **Area:** protocol-design

`Message::encode` writes `dst.write_u32_le(self.payload_size() as u32, "Message.payload_len")` (message.rs:292) with no `try_from` check, while `Encode::size()` (message.rs:278-280) returns `usize`. On 64-bit, a `FrameData` whose payload exceeds 4 GiB truncates the header length while `size()` and the actual write remain correct — producing a frame whose declared length disagrees with its content. Today's inner-field checks partially mask this (FrameData::encode_payload does `u32::try_from(self.data.len())` at message.rs:203, WindowCreated does the same for title at :133), so the truncation needs `payload_size()` itself to exceed u32, which requires a >4 GiB frame — unrealistic now. But once the length field is made authoritative (as it must be), any encode/header disagreement becomes a decode failure or a desync rather than a benign inconsistency, so this should be a hard error, not a cast. It is a one-line fix with a test.

**Fix.** Replace with `u32::try_from(self.payload_size()).map_err(|_| EncodeError::FieldTooLarge { context: "Message", field: "payload_len" })?`, and add a per-message-type maximum payload constant that `encode` enforces.

<details><summary>Verification</summary>

Verified — the code facts are exact, but one premise of the claim is wrong and reachability is narrower than stated.

CONFIRMED: message.rs:292 is `dst.write_u32_le(self.payload_size() as u32, "Message.payload_len")?` with no try_from; size() at :278-280 returns usize; the checked `u32::try_from` at :203 and `u16::try_from` at :133 are real and in the same file, so this is a genuine deviation from the file's own invariant-checking discipline.

CLAIM'S PREMISE IS WRONG (in the finding's favor): it argues the bug matters "once the length field is made authoritative (as it must be)". It already is authoritative. oxtransport/src/stream.rs:30-40 reads the u32 header and sizes the payload read from it, and Message::decode (message.rs:300) discards `_payload_len` entirely — the transport header is the sole framing authority. A truncated header is a live stream desync today, not a latent one.

REACHABILITY IS NARROWER THAN CLAIMED: FrameData::payload_size() is 14 + data.len(). Truncation needs 14 + len > u32::MAX, while the inner try_from at :203 rejects len > u32::MAX. So the silent-corruption window is exactly 14 values wide — data.len() in 4294967282..=4294967295. Anything larger yields a clean FieldTooLarge. Additionally: encode_vec (codec.rs:41) must first allocate a >4 GiB zeroed Vec; the read side caps at MAX_MESSAGE_LEN = 64 MiB so a decoded frame can never be re-encoded into that window; and FrameData has no production construction site yet (grep finds it only in tests — WGC capture is unwritten P1c/P1d). ROADMAP: docs/HANDOFF.md marks "P0 oxproto — protocol messages" complete and has no hardening/fuzzing/validation item in P1c-P5, so this won't be revisited by roadmap flow. It is not a pending next-step item; it sits in code the roadmap considers finished.

VERDICT: real but genuinely low — unreachable in practice, no security or correctness impact today. Justified only as a one-line consistency fix (swap the cast for u32::try_from + EncodeError::FieldTooLarge, matching :203/:133) so the envelope can never silently disagree with its payload.

MISSED NEIGHBOR (different, strictly more reachable finding): write_message (oxtransport/src/stream.rs:10-18) has no size guard while read_message_bytes enforces 64 MiB, so the agent can successfully encode and send a frame the client will always reject as "oxproto message too large".
